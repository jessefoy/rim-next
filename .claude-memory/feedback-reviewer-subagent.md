For non-trivial diffs (more than a one-liner — new logic, multi-file changes, schema-adjacent work, anything that changes a query or render path), spin up a code-reviewer sub-agent on the staged diff before committing. Hand it a RIM-specific checklist: RSC serialization (raw `Date` crossing server→client), env-var trim (`NEXTAUTH_URL`-derived constants), `sendTemplatedEmail` calls without a matching seed in `prisma/migrate.mjs`, cache-of-source-fields patterns, `void (async)` in route handlers, `Array.isArray` filters that silently reject HTML, design-token discipline (no raw hex/px), per-render effect thrash (deps that recreate every render).

**Why:** RIM's recurring failure mode is *categorical drift* — bugs that pass `npm run build` and only surface when behavior changes. Session 97 had `Array.isArray(doc.body)` rejecting HTML. Session 96 had `NEXTAUTH_URL` trailing space breaking email links. Session 109 had cache-of-source freezing program labels. Session 116 nearly shipped a non-deterministic `take: 20` after dropping `orderBy`, a 365-day day-walk for past non-recurring anchors, a stale-pill rendering for past registrations, and a visual regression. Session 117 first run flagged a `participants.length+1` mismatch with rendered rows; second run flagged a `useTracks`/`useSpeakingParticipants` effect re-running every render with no identity-based short-circuit (which would have caused dispatch loops in the speaker auto-pin) plus `as never` casts in a device-picker call hiding a real signature mismatch.

The reviewer sub-agent looking specifically for those categories on the fresh diff catches them; the main loop misses them because it has fresh context on what changed but not on the surrounding invariants.

**How to apply:** Run before commit on any non-trivial change. Use `general-purpose` agent type with a tight prompt naming the specific patterns to look for; if relevant, include the path to the plan file so the reviewer knows the intended scope. Skip for truly small fixes (typos, one-line tweaks). When the reviewer flags something: address it before commit, don't push and patch. The point is the fresh-eyes catch, not the round-trip. If the reviewer flags a false positive (e.g. session 117 round 1 worried about an `onLeave` wiring that actually flowed through `LiveKitRoom.onDisconnected`), verify with a quick read rather than blindly applying the suggestion — but the false-positive rate has been ~25% so far, low enough to be worth running.
