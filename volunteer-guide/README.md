# The RIM Guide

What volunteers' shared Claude project ("RIM Guide", in RIM's Claude for Nonprofits workspace) knows, so they can ask how the site works and why, look at it as they see it, and turn what they notice into a clear note for Jesse. Started 2026-10-27.

**How it reaches the project:** the **RIM Guide connector** (`app/api/guide-mcp/[key]/route.ts`) serves everything, read live. The project holds only the instructions. A push to `main` updates the guide; nothing is uploaded by hand.

**Each volunteer signs in (2026-10-27).** The connector asks each person to sign in with their own RIM account (OAuth with PKCE, RIM as its own sign-in: `lib/guideAuth.ts`, `app/api/guide-oauth/*`, the Allow page `app/guide/connect/page.tsx`). It then reads what that person can read on the site, through the site's own gates, with their roles read fresh on every call. Read-only, except for Content editors (below). Sign-ins are kept by hash in `guide_grants`; access lasts an hour and renews itself; a code or renewal used twice ends that connection.

**What it serves:**
- The topics here, `1-…` to `6-…` (every `<number>-<name>.md`; the name after the number is the topic's name), and the design docs listed in `DESIGN_DOCS` in `lib/guideContent.ts` (the intentions; not the session log, UP_NEXT, the backlog, the stack reference or the sign-in doc).
- **Every signed-in screen's words and code**, for the screens in `screens.json`. The words (labels, hints, buttons, messages, with file and line) are pulled from the code at build time by `scripts/guide-screens.mjs` into `generated-screen-words.json` (not committed). Add a screen to `screens.json` when one is built; a folder entry takes new files automatically.
- The public pages' words, read live.
- **RIM's data, as the person sees it** (`lib/guideData.ts`): programs and their settings (`canUsePrograms`), people registered with answers, notes and history (`canUseRegistration`; dana amounts only with `canSeeDanaAmounts`), the email templates (ADMIN, like `/admin/emails`), members (ADMIN or REGISTRAR, section by section as the Member Registry shows them), and their teams' members, conversations and schedule (`canAccessHub`, `canAccessHubScheduler`).

**The guide acts for each person (2026-10-28, phase 1 of "an alternative interface for the whole RIM Next webapp", Jesse).** It does what their account may do on the site, through the site's own steps, never more: `reachOf` and `fieldsFor` in `lib/guideEdits.ts` ask the same gates as the routes (`canUsePrograms` to start and change programs, with every editor part, teachers and teams included; `canUseProgramManager` to archive; the Course Manager's `hasToolAccess` for courses and lessons; ADMIN for emails and teacher pages). Tools: `create_program` (blank, a shape, or a copy, through `createProgram`), `archive_program` (`setProgramArchived`), `read_content` and `edit_content`. Every change is in the History and emailed to Jesse. **Phase 2, Registration (2026-10-28):** for those with `canUseRegistration`, `lib/guideRegistration.ts` (add someone, change a registration, notes, remove a cancelled one, message people, the reminder, registration settings) through the app's own steps, moved unchanged into `lib/registrationActions.ts`, so each action writes the program's History as the person. **Ask first:** any guide action that would email anyone does nothing on its first call; it says who would be emailed and what, with a signed slip (`confirmOrAsk`: this person, tool, these details and exactly that description, 15 minutes, signed with a key from `AUTH_SECRET`). Only a second call that hands the slip back goes ahead, and only if the description, worked out again, is unchanged, so a yes can't approve something different (the last place filled meanwhile, another address). Each slip works once (kept by hash in `guide_grants`, kind `confirm`, until it expires), so a retry can't send a message or post twice. It is in the tool, so the guide can't skip it: Registration's actions, and a program start or change that emails teams or hosts (`newProgramEmails`, `programChangeEmails`, including a team unticked, and `scheduledEmails`: a change that makes the reminder or the note after go out within a day). A new action that emails must ask first the same way. **Phase 3, teams (2026-10-28):** `lib/guideSchedule.ts` for anyone on a team: take, give up, ask for cover, cover, clear a request, and post or reply in Conversations; for a team's own lead (or Scheduling managers and admins), put someone on, take someone off, take a session over. Through the Scheduler's and Conversations' own steps, moved unchanged into `lib/scheduleActions.ts` and `lib/teamActions.ts`, which check the same permissions as the buttons. An email only to the person asking (their own confirmation) is said in the answer without a second yes; everything that emails others asks first. Rotations, resets and team membership stay on the site (Jesse). **Planned:** phase 4 creating courses and lessons. Each new action moves its route's steps into a shared function first, as the program save, create and archive did.

**Content editors change the site's content (2026-10-28).** Jesse gives the **Content editor** role (`CONTENT_EDITOR`, Roles & access in the Member Registry) to people he trusts, and only for them the connector adds `read_content`, `edit_content`, `find_page_words` and `change_page_words` (`lib/guideEdits.ts`). There is no approval step (Jesse: "Whoever I give permission … I trust"); the guide shows each change before and after and waits for the person's yes.
- **What the editors save** (programs, courses, lessons, emails, teacher pages; never the sign-in emails or `content-changed`, and never an email's on/off) changes through the editors' own save functions, shared with their routes (`lib/programSave.ts`, `lib/contentSaves.ts`), so a change does exactly what Save does on the site: a program's new name reaches its registrations, donations and Zoom meetings, a schedule change clears sessions, the "someone else changed this meanwhile" check applies. Setting a whole part needs the version `read_content` gave, so nothing saved since is overwritten; changing words inside a part works on the part as it is now. Rich text is set only as HTML (cleaned when shown), never as an object; lists only where a part is a list. An item is found only when one matches. **Content only:** the parts that decide who may see or reach something (a program's teachers, guest and open entry, its hosting, supporting and preparing teams, its mailing list; a course's roles, self-enrolment and onboarding; a lesson's access and teachers) are not offered, and stay with the editors on the site (`ACCESS_PARTS` and the field lists in `lib/guideEdits.ts`). Change an editor's save in those files, never in its route.
- **The words written into the pages' code** (Home, About and the other pages, the member and team screens' labels; never `app/api`, `app/admin`, `app/login`, `app/guide`, or a file with server actions) change by one commit to `main` on GitHub for all the changes in a call, all or nothing (`lib/pageWords.ts`, through the Git Data API), which Vercel deploys in a minute or two. A find counts only where it is page words, so the same words in code don't block it; an entity in the new words (`&nbsp;`) is kept as written, and a space at either end is written `&#32;` so a line break in the code can't drop it. Words only, by an allowlist (`wordsOnlyChange` + `notWords`, a TypeScript comparison): the file must read exactly as before except for text between tags, a quoted string shown between tags, the alt/title/aria-label/placeholder/label attributes, and the values of word names (title, description, label, body…) in lists of words and the metadata. Anything else, a role check, an address, a class, a directive, is refused (review, 2026-10-28: a blocklist let a role check through). The repository is public, so the commit names no one. **Before pushing, pull: Content editors commit to `main` too.**
- **Every change is kept, and Jesse gets one email each evening:** `content_changes` (who, when, what, each part before and after, the commit), listed newest first at `/admin/content-changes` with a page for each. The changes that shape the site (`inDaily`: programs, courses, lessons, emails, teacher pages, page words, registration settings) go in one email each evening, 01:00 UTC (`/api/cron/content-changes-daily`, `sendDailyChanges`, the `content-changes-daily` template; `sentAt` marks what went, set only once the email is accepted; nothing on a quiet day). The everyday actions people do in the apps (sessions, cover requests, conversations, Registration actions on a person) are recorded with `inDaily` false and not emailed (Jesse, 2026-10-28). `CONTENT_CHANGES_EMAIL` overrides the address. The earlier `content-changed` template (one email per change) is no longer sent.
- Setup: `GITHUB_CONTENT_TOKEN` in Vercel (a fine-grained token for this one repository with Contents read and write; it has an end date, so it needs renewing). Without it, or once GitHub refuses it, page words can't change and the guide says which.

Email addresses (other than Jesse's) and anything shaped like a key are blanked in the topics, docs and code it serves. People's details come only through the data tools, behind the gates.

**Keeping it current:** when a session changes something a topic describes, update that topic in the same commit. Screen words, design docs and public pages need nothing: they are read from the deploy.

- `INSTRUCTIONS.md` is pasted into the project's **Set project instructions**. Not served by the connector. If it changes, paste it again (the one manual step).
- This README is not served.

**Setup (once):** `GUIDE_CONNECTOR_KEY` (a random string of 24+ characters) is set in Vercel; the sign-in signs with a key derived from `AUTH_SECRET`, so it needs no setting of its own. A workspace owner adds the connector in Claude (Organization settings > Connectors > Add > Custom > Web) at `https://rim-next.vercel.app/api/guide-mcp/<the key>`; after the domain move the address changes with it, and the connector must be re-added. Each volunteer presses **Connect** (Customize > Connectors), signs in to RIM in the window that opens, and presses **Allow**. Verified 2026-10-27: the connector works in chats inside the shared project.

**For volunteers:** `Getting started with the RIM Guide.pdf` (made from `getting-started.html` by printing it with headless Chrome) walks someone new to Claude through joining, connecting, opening the project and sending a note.
